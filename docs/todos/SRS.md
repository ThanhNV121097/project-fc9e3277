## 1. Purpose

A single-page todo list web app that lets any visitor add tasks, mark them complete, and delete them. Tasks are persisted server-side in PostgreSQL so they survive page reloads and browser restarts. No authentication is required; every visitor operates on the same shared task list. If this module is removed, the product ceases to exist.

## 2. Actors

| Actor | Who they are | What they may do in this module |
|---|---|---|
| Visitor | Any person with a browser | View all tasks, add a task, complete a task, delete a task |

There is one shared list; there are no accounts, roles, or permissions beyond the above.

## 3. Scope

**In scope** — the functions specified below, by their plan titles:

- Task list with empty state
- Add a task
- Complete a task
- Delete a task

**Out of scope** — name what a reader would reasonably expect here and say where it lives instead.

- User accounts and authentication — deliberately not built; no login is required per the product brief.
- Task editing (renaming a task) — belongs to a future `todos` enhancement; not in the current plan.
- Task categories, priorities, or due dates — not in the current plan.
- Pagination — not required for a simple shared list.

### 4.1 Task list with empty state

**Requirement TODOS-001 — Load and display task list**

*As a* Visitor, *I want to* see every saved task on the page when it first loads, *so that* I know what work is already recorded.

Behaviour:

1. On page load the browser requests the full task list from the backend.
2. While waiting for the response the UI shows a loading indicator.
3. When the response arrives with one or more tasks, the loading indicator is replaced by the task list. Each task is rendered with its current `completed` state reflected visually.
4. When the response arrives with zero tasks, the loading indicator is replaced by a friendly empty-state message.
5. When the response fails, the loading indicator is replaced by an inline error message and a retry control.

**Acceptance criteria** — each maps one-to-one onto a test case in `docs/todos/test-cases/task-list.md`.

| # | Given | When | Then |
|---|---|---|---|
| AC-1 | There are saved tasks in the database | The page loads | All tasks appear in the list with correct `completed` visual state |
| AC-2 | There are no saved tasks | The page loads | A friendly empty-state message is shown, not a blank screen |
| AC-3 | The backend is unavailable | The page loads | An error message and a retry control are shown |
| AC-4 | The page is already displaying tasks | The backend returns an updated list | The display updates to reflect the new list |

**Failure, boundary and permission behaviour**

| Case | Condition | Expected behaviour |
|---|---|---|
| Network failure on load | Backend unreachable | Inline error message ("Could not load tasks. Check your connection and try again.") with a Retry button; the page does not crash or go blank |
| Partial response | Backend returns malformed JSON | Console error logged; user sees generic error message with retry |
| Zero tasks | No rows in database | Dedicated empty-state panel shown; no spinner, no error |

**Data touched**

| Field | Type | Required | Rule |
|---|---|---|---|
| id | integer | yes | Primary key, auto-generated by the database |
| title | text | yes | Non-empty, max 500 characters |
| completed | boolean | yes | Default false |

### 4.2 Add a task

**Requirement TODOS-002 — Create a new task**

*As a* Visitor, *I want to* add a new task by typing its title and submitting, *so that* it appears in the list immediately and is saved permanently.

Behaviour:

1. The page displays a text input labelled "Add a task…" and a button labelled "Add".
2. The visitor types a title into the input.
3. Pressing Enter or clicking "Add" submits the input value.
4. If the trimmed value is non-empty the task is sent to the backend and saved to the database.
5. The new task appears at the bottom of the list immediately (optimistic insert) before the server confirms.
6. If the save fails the task is removed from the list and the input is restored with the original value; an inline error is shown.
7. After a successful save the input is cleared and focus remains in the input field.

**Acceptance criteria**

| # | Given | When | Then |
|---|---|---|---|
| AC-1 | The input contains non-whitespace text | Enter is pressed | A new task with that title appears in the list; the input is cleared |
| AC-2 | The input contains non-whitespace text | "Add" is clicked | Same result as AC-1 |
| AC-3 | The input is empty or contains only spaces | Enter is pressed | No task is created; no error shown |
| AC-4 | The input contains only spaces | "Add" is clicked | No task is created; no error shown |
| AC-5 | A task was optimistically added but the save failed | The server returns an error | The failed task is removed from the list; the input is restored with the original text; an inline error is shown |
| AC-6 | The page already shows tasks | A new task is added | The new task appears at the bottom of the list without disturbing existing tasks |
| AC-7 | The input holds text | The page is reloaded | The input is empty (no persistent draft) |

**Failure, boundary and permission behaviour**

| Case | Condition | Expected behaviour |
|---|---|---|
| Empty input | Trimmed value is "" | Input is left unchanged; no network call made; no error message |
| Whitespace-only input | Trimmed value is "" | Same as empty input |
| Boundary: max length | Title is exactly 500 characters | Accepted and saved successfully |
| Boundary: over max length | Title is 501 characters | Rejected with an inline error message naming the limit ("Title must be 500 characters or fewer") |
| Server error on save | Backend returns 5xx | Task removed from list; input restored; inline error shown |
| Concurrent adds | Two visitors add tasks simultaneously | Both tasks appear in the list; no data is lost |

**Data touched**

| Field | Type | Required | Rule |
|---|---|---|---|
| title | text | yes | Non-empty after trim, max 500 characters |
| completed | boolean | yes | Always false on creation |

### 4.3 Complete a task

**Requirement TODOS-003 — Toggle task completion**

*As a* Visitor, *I want to* mark a task as complete or undo that mark, *so that* the list reflects what is done.

Behaviour:

1. Each task row displays a checkbox or toggle control indicating its current `completed` state.
2. Clicking the control sends a completion-toggle request to the backend.
3. On a successful response the task's visual state updates (strikethrough + muted colour for complete; normal otherwise) immediately.
4. The completed state is persisted and survives a page reload.

**Acceptance criteria**

| # | Given | When | Then |
|---|---|---|---|
| AC-1 | A task is incomplete | Its checkbox is clicked | The task's visual state changes to complete (strikethrough + muted); the change persists after reload |
| AC-2 | A task is complete | Its checkbox is clicked | The task reverts to the incomplete visual state; the change persists after reload |
| AC-3 | A task is complete | The page is reloaded | The task is still shown as complete |
| AC-4 | A task is incomplete | The page is reloaded | The task is still shown as incomplete |
| AC-5 | The toggle request fails | The server returns an error | The visual state reverts to what it was before the click; an inline error is shown |

**Failure, boundary and permission behaviour**

| Case | Condition | Expected behaviour |
|---|---|---|
| Server error on toggle | Backend returns 5xx | UI reverts to the prior visual state; inline error shown; no data inconsistency |
| Task not found | The task row was deleted by another visitor while the page is open | Error returned; the task disappears from the list with no crash |

**Data touched**

| Field | Type | Required | Rule |
|---|---|---|---|
| completed | boolean | yes | Toggled; server-side timestamp of toggle not required |

### 4.4 Delete a task

**Requirement TODOS-004 — Delete a task**

*As a* Visitor, *I want to* delete a task by clicking a Delete button, *so that* it disappears from the list and the database immediately without a confirmation prompt.

Behaviour:

1. Each task row has a Delete button (visible at all times or revealed on hover).
2. Clicking Delete immediately removes the task from the visible list (optimistic delete).
3. A delete request is sent to the backend.
4. If the request fails the task re-appears in the list at its original position and an inline error is shown.
5. No confirmation dialog is shown before deletion.

**Acceptance criteria**

| # | Given | When | Then |
|---|---|---|---|
| AC-1 | A task is visible in the list | Delete is clicked | The task disappears from the list immediately; no confirmation dialog is shown |
| AC-2 | The delete request succeeds | Delete is clicked | The task is removed from the database |
| AC-3 | The delete request fails | Delete is clicked | The task re-appears in the list at its original position; an inline error is shown |
| AC-4 | The page is reloaded | After a successful delete | The deleted task does not re-appear |
| AC-5 | A task is deleted | The remaining tasks are still displayed | No other tasks are disturbed |

**Failure, boundary and permission behaviour**

| Case | Condition | Expected behaviour |
|---|---|---|
| Server error on delete | Backend returns 5xx | Task re-appears in the list at its original position; inline error shown |
| Task not found | The task was already deleted | Backend returns 404; the UI silently removes the task (already gone, no error needed) |

**Data touched**

| Field | Type | Required | Rule |
|---|---|---|---|
| id | integer | yes | Used to identify the row for deletion |

## 6. Non-functional requirements

Only what is real for this module.

| Area | Requirement |
|---|---|
| Performance | Page load with up to 1,000 tasks responds within 2 s on a typical broadband connection |
| Performance | Add / complete / delete actions reflect in the UI within 200 ms of the server response |
| Accessibility | All interactive elements are keyboard-reachable; focus is visible; inputs have associated labels; colour contrast ≥ 4.5:1 for all text |
| Responsive | Works at 320 px and up; no horizontal page scroll on any supported viewport |
| Privacy | No personal data is collected; the single shared task list is public to all visitors |
